# Korean Microstyle LLM — 개선 제안본

원본: `korean_microstyle_llm_project.md`
이 문서는 원본의 핵심 아이디어("눈치 + 말맛" 듀얼 레이어)를 유지하되, 실현가능성 분석에서 드러난 약점을 보강한 개정안이다.

| 영역 | 원본 | 개정 |

## 1. 핵심 컨셉 (원본 유지)

"재미있는 답변 생성기"가 아니라 "눈치 보고 웃기는 모델".

```text
사용자 입력
→ Thinker: 보수적 상황/감정/관계/위험도 판단
→ Speaker: 그 안에서만 말맛 있게 표현
→ 최종 답변
```

이 부분은 원본 그대로 가져간다. 듀얼 레이어 분리는 디버깅 가능성, 안전성, 작은 모델 학습 신호 면에서 합리적.

---

## 2. 기반 모델 — 사전 검증 항목

원본 `gemma4:e4b`는 2026-05 기준 공식 발표를 확인 못 했다. 시작 전에 다음 확인:

```text
ollama search gemma
ollama search exaone
ollama search qwen
```

**후보군 (한국어 능력 + RTX 3080 / 16GB RAM 기준):**

| 모델 | 크기 | 한국어 | QLoRA 4-bit VRAM | 비고 |
|---|---|---|---|---|
| `gemma3:4b` (확인 필요) | 4B | 보통 | ~6GB | 원본 의도에 가장 가까움 |
| `gemma3n:e4b` (확인 필요) | effective 4B | 보통 | ~5GB | 모바일/edge 최적화 |
| `exaone3.5:2.4b` | 2.4B | **강함** (LG, 한국어 특화) | ~4GB | 작아서 학습 빠름 |
| `qwen2.5:3b` | 3B | 좋음 | ~5GB | 다국어, instruction tuning 안정적 |

**선택 기준:** 한국어 구어체·축약어 처리 성능을 zero-shot으로 비교 → 가장 잘 받아치는 놈으로. Phase 1 프롬프트 프로토타입 단계에서 4개 모두 같은 입력 30개 돌려보고 결정.

`참고` 링크의 arxiv ID `2601.21459`도 실재 확인 필요. 자릿수가 어색하다.

## 3. 데이터 전략 — Thinker와 Speaker 분리

원본의 "데이터 100~300개"는 단계 구분 없이 묶어 위험하다. 분리:

### 3.1 Thinker 데이터 (적고 정확하게)

- **목표량: 200~500개**
- 형식: `{입력, 판단 JSON}`
- 출처: 사용자 직접 작성 + 합성 (LLM이 입력 생성 → 사람이 판단 검수)
- 핵심: 분류 일관성이 양보다 중요. **같은 입력에 다른 사람이 라벨링했을 때 80% 일치**가 목표.

### 3.2 Speaker 데이터 (넓고 다양하게, 단 라벨 필수)

- **목표량: 2,000~5,000개** (원본 100~300개로는 LoRA가 안 익는다)
- 형식: `{입력, Thinker 판단, style_control 태그, 답변}`
- 출처 3-소스 혼합:
  1. **합성 (60%)**: LLM이 (판단 JSON + style 태그) 조건 하에 답변 생성 → 사용자가 좋은/나쁜 선별
  2. **직접 작성 (20%)**: 사용자 본인 말투 anchor + 친구 대화 발췌 (동의 받은 것만)
  3. **유튜브 자막 (20%)**: 보조용. 노이즈 많고 저작권 회색지대라서 메인 의존 금지

### 3.3 자막 사용 시 주의

- **자동 자막은 초성/축약어에서 망가짐.** "ㄱㄱ"이 "구구"로 잡힌다. 수동 자막만 사용.
- **저작권:** 학습 데이터 용도면 라이선스 검토 필수. 영상 제작자에게 동의 받기 어렵다면 **태그 추출용으로만** 쓰고 raw text는 dataset에 안 넣는 방식 권장.
- 그래서 자막은 "현실 대화 패턴 관찰용 reference"지, "학습 corpus" 아님.

## 4. Annotator 모델 — 비용/약관 결정 먼저

원본 흐름:
```
자막 → Annotator 모델이 다축 라벨 생성 → 사람 검수
```

**문제:** Annotator의 안정성이 전체 파이프라인의 병목.

- 로컬 작은 모델(4B 이하)로 10축 JSON 안정 출력은 불안정. 분산이 크다.
- GPT-4o / Claude API로는 가능하지만 **비용 발생**. CLAUDE.md "돈 들어가는 일은 사용자 확인" 규칙 적용 대상.

**의사결정 분기 (Phase 2 진입 전 사용자에게 확인):**

| 옵션 | 비용 | 품질 | 데이터 양 한계 |
|---|---|---|---|
| A. 외부 API (Claude Haiku 등) | 1000건 기준 $1~5 | 높음 | 사실상 무제한 |
| B. 로컬 모델 + 사람 검수 강화 | 0 | 중간 (검수 필수) | 사람 작업량이 병목 |
| C. 사용자가 직접 라벨링 | 0 | 높음 | 수백 건이 한계 |

**권장:** 첫 100건은 C로 시작 (분류 체계 다듬기), 안정되면 A로 확장.

## 5. 평가 체계 — Phase 1에서 먼저 짠다

원본은 평가가 마지막에 등장한다. **이게 가장 큰 함정.** 학습 → 평가 → 재학습 루프가 평가 비용으로 막힌다.

### 5.1 LLM-as-judge rubric (Phase 1에서 정의)

5개 축으로 1~5점 평가. 각 축은 외부 LLM이 판정 가능한 객관 기준으로 작성:

```text
1. 상황 적합성   — 판단이 입력 맥락과 일치하는가
2. 유머 적절성   — 허용 범위 안에서 멈췄는가 (overshoot 감점)
3. 자연스러움    — 구어체 리듬이 인공적이지 않은가
4. 대화 유지력   — 답변 후 대화가 이어질 만한가
5. 안전성        — 조롱·실패 확정·과한 밈 없음
```

### 5.2 평가 데이터셋 고정

- **검증 케이스 50개**를 Phase 1에서 미리 만들어 두고 절대 학습에 안 쓴다.
- 이후 모든 변경(프롬프트 수정, LoRA 학습, 모델 교체)을 이 50개에 돌려서 회귀 추적.

### 5.3 사람 평가는 spot-check

- 50개 중 무작위 10개만 사람이 보고 LLM-judge 점수와 비교.
- 일치율이 70% 넘으면 LLM-judge 신뢰. 아니면 rubric 다시 다듬기.

---

## 6. 태그 체계 — MVP는 4축만

원본은 social_function 13 + 말투 10 + style_control 6축 = 조합 폭발. 데이터 100~300개로는 분포 90% 비어 있다.

**MVP 4축으로 축소:**

```json
{
  "humor_level":    ["none", "light", "medium"],
  "reply_function": ["위로", "동의", "받아치기", "정정", "수습"],
  "energy":         ["low", "medium", "high"],
  "risk":           ["low", "high"]
}
```

- 조합 수: 3 × 5 × 3 × 2 = **90개 셀.** 데이터 500개면 셀당 5~6개 확보 가능.
- Phase 3에서 데이터 분포 보고 확장 결정. 자주 안 쓰이는 축은 끝까지 안 추가해도 됨.

원본의 풍부한 분류는 **데이터셋 메타데이터로는 남겨두되, 모델 입력 라벨에서는 제외.**

---

## 7. 백업 구조 — 단일 모델 멀티태스크 비교

원본은 Thinker / Speaker 별도 LoRA 2개. 이게 안 풀릴 경우 대비:

**Plan B: 한 모델 멀티태스크**

```text
입력: 사용자 발화
출력: <judgment>...</judgment><reply>...</reply>
```

- 한 시퀀스에 판단 + 답변을 같이 생성.
- 장점: 추론 호출 1회, 학습 어댑터 1개, 정보 손실 없음.
- 단점: 디버깅 어려움, judgment가 reply에 leak 될 수 있음.

**비교 실험:** Phase 4 진입 시 두 방식 모두 200개 작은 데이터로 학습해서 평가셋 점수 비교 후 선택.

## 8. 단계별 로드맵 (개정)

각 단계를 **별도 PLAY**로 분리. CLAUDE.md "PLAY 간 의존 금지" 규칙에 맞춰 데이터/스펙은 README로 전달.

### PLAY{N}_microstyle_prompt (Phase 1)

- 학습 없이 Thinker/Speaker를 프롬프트로 구현.
- 4개 후보 모델(gemma3, exaone3.5, qwen2.5 등)로 같은 입력 30개 돌려 비교.
- **LLM-judge rubric + 평가 케이스 50개도 여기서 같이 만든다.**
- 산출물: 선정된 기반 모델 + 평가셋 + 두 프롬프트 템플릿.
- 디스패치 적합도: **높음** (외부 API 1회 호출이거나 ollama 로컬).

### PLAY{N+1}_microstyle_dataset (Phase 2~3)

- Annotator 결정(사용자 확인 후 A/B/C 옵션 선택).
- Thinker 200~500개 + Speaker 2,000~5,000개 수집.
- MVP 4축 태그 체계 적용.
- 산출물: `thinker_dataset.jsonl`, `speaker_dataset.jsonl`.
- 디스패치 적합도: **중간** (대용량 합성 시 외부 API 비용·시간 주의).

### PLAY{N+2}_microstyle_train (Phase 4~5)

- Thinker LoRA 학습 → 평가셋 회귀 확인.
- Speaker LoRA 학습 → 평가셋 회귀 확인.
- 동시에 Plan B(멀티태스크 단일 모델)도 학습해서 비교.
- **디스패치 부적합** (학습은 분 단위 이상). 사용자가 로컬에서 직접 실행하는 PLAY로 README "실행법"에 명시.

### PLAY{N+3}_microstyle_eval (Phase 6)

- 최종 모델 + 평가셋 + 사람 spot-check 인터페이스.
- 산출물: 비교 리포트(원본 모델 vs Thinker+Speaker vs 멀티태스크).

## 9. 학습 하이퍼파라미터 (원본 유지 + 보강)

원본 값들은 RTX 3080 기준 적절. 추가 권장:

```text
학습 방식: QLoRA 4-bit (bitsandbytes)
LoRA rank: 8 (작게 시작, 부족하면 16)
LoRA target: q_proj, v_proj (최소). 부족하면 k_proj, o_proj 추가
batch size: 1
gradient accumulation: 16
sequence length: 1024 (Speaker는 판단 JSON 길이 고려해서 2048도 가능)
learning rate: 2e-4 (LoRA 일반)
warmup ratio: 0.03
epoch: 2~3 (overfit 빠름. 평가셋 점수로 early stop)
```

**모니터링:** 학습 중 매 epoch마다 평가셋 50개 돌려서 점수 추이 기록. 평균 점수가 하락 시작하면 stop.

## 10. 리스크 우선순위

| 순위 | 리스크 | 완화책 |
|---|---|---|
| 1 | 평가 체계 부재로 학습 루프 막힘 | Phase 1에서 rubric + 50케이스 미리 고정 |
| 2 | Annotator 비용/품질 미결정 | Phase 2 진입 전 A/B/C 옵션 사용자 결정 |
| 3 | 기반 모델 식별 오류 | Phase 1에서 4개 후보 실측 비교 |
| 4 | Speaker 데이터 부족 | 합성 60% + 직접 20% + 자막 20% 혼합으로 양 확보 |
| 5 | 태그 폭발로 학습 신호 희석 | MVP 4축으로 시작, 분포 보고 확장 |
| 6 | 2단 호출 불안정 (JSON 깨짐) | 멀티태스크 단일 모델 백업안 병행 |
| 7 | 자막 저작권 회색지대 | 자막은 패턴 관찰용, dataset에 raw 포함 금지 |

## 11. 핵심 문장 (원본 + 추가)

> 재미있는 출력은 자유롭게, 분류와 판단은 보수적으로.
> 재미있는 말투를 학습시키는 것이 아니라, 재미가 허용되는 조건을 학습시킨다.

**여기에 추가:**

> 학습보다 평가가 먼저다. 평가셋 없는 LoRA는 굴러갈 수 없다.
> 그리고 한 PLAY가 모든 단계를 떠안지 않는다. PLAY는 작게, 자주 끊는다.
